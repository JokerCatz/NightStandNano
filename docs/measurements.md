# 量測紀錄

工具：`tools/stress.py load`（各情境 8–10 秒，讀 `st` 的 `cpu`、`mem`、`big`、`und`）、`tools/stress.py leak N`、UART 指令 `memwatch [秒]`（每 10 ms 取樣內部 RAM，找短暫低點）。
板子：ESP32-S31 開發板，Wi-Fi + Classic 藍牙 + BLE 都開著，輸出到 USB 小尾巴。

結論：
- BLE 用戶端連線並監看頻譜的成本：核心 0 約 +6%，核心 1 約 +2%，內部 RAM 約 −4 KB。
- 單純播放很輕；全部音效一起開約佔核心 1 的 60%。場景＋全部音效到 94%，沒有斷音但沒有餘裕。
- 場景比其他來源多用約 26 KB 內部 RAM（Ogg 解碼器的配置），最大連續區塊降到 35 KB。
- 未量：藍牙耳機輸出（AAC／SBC／LDAC 編碼）與音效同開。LDAC 約佔半顆核心（round 的數據），已設規則：LDAC 時重型音效自動暫停。

## 注意
`heap_caps_get_minimum_free_size(MALLOC_CAP_INTERNAL)` 在這塊板子上不可信：它是各記憶體區各自最低值的總和，一開機就比實際可用值低約 65 KB（開機時 free 306 KB、「min」241 KB）。所以 `st` 不回報它，改回報 `big`（最大連續區塊）；要看真正的短暫低點用 `memwatch`。

## 2026-11-25 Auracast 廣播（`out cast`）
設定：BLE 5.0 功能集＋LE Audio 廣播來源（與 JukeDial 相同），LC3 48 kHz 立體聲（2 個 BIS，各 120 位元組／10 ms），Wi-Fi 開著，Classic 藍牙開著。

**記憶體（內部 RAM 剩餘／最大連續區塊）**
| 狀態 | 套用 Wi-Fi 精簡前 | 套用後 |
|---|---|---|
| 待機，未啟動 LE Audio | 78 KB / 45 KB | 112 KB / 63 KB |
| 廣播中，沒有播放 | 46 KB / 32 KB | 79 KB / 47 KB |
| 廣播＋AAC 電台 | 32 KB / 31 KB | 69 KB / 35 KB |
| 廣播＋場景 | **當機**（藍牙控制器 assert，記憶體用盡） | 53 KB / 32 KB（瞬間最低 50 KB） |

- LE Audio 啟動本身約佔 26 KB，開始廣播再佔約 6 KB。
- 「Wi-Fi 精簡」＝JukeDial 量過並在用的設定：靜態 TX 緩衝 16→6、Wi-Fi 熱路徑改從 flash 執行。合計多出約 33 KB。
- 打開 BLE 5.0＋ISO 設定與 1 ms tick 本身（不啟動 LE Audio）讓待機少約 25 KB；精簡後整體反而比原本多。

**CPU（核心 0／核心 1）**：廣播待機 15% / 19%；廣播＋電台 18% / 24%；廣播＋場景 19% / 47%；廣播＋資料夾播放（測試用正弦波檔）18% / 79–90%。LC3 每聲道每 10 ms 約 1.0–2.4 ms，隨訊號內容變化。

**接收品質**：JukeDial 用 `btmode 4` 收聽 Nano 的廣播，兩個串流都建立。Nano 同時開 Wi-Fi 電台、BLE 用戶端連線並訂閱頻譜時，2000 個音框中補償 22 個（約 1.1%）；JukeDial 自己的文件記載 Wi-Fi 開著時約 1.6%。Nano 端 underflow 0、送出錯誤 0。

**BLE 控制與廣播並存**：可以。廣播中 BLE 用戶端可連線、下指令、收頻譜（約 30 幀/秒）。
- 限制：LE Audio 第一次啟動時不能有 BLE 連線，否則 IDF 會 assert（`esp_ble_iso` 的 GATT 連線回呼在佇列建立前就被呼叫）。做法：啟動前先中斷用戶端並停止廣告，啟動完再恢復，用戶端重連即可（約 0.3 秒）。
- LE Audio 啟動後無法卸載，那 26 KB 要重開機才會還回來；停止廣播（改回其他輸出）只會拿掉串流與廣告。

## 2026-11-25 藍牙耳機輸出（AAC，對 JukeDial）與音效
| 情境 | 核心 0 | 核心 1 | 結果 |
|---|---|---|---|
| FLAC 48 kHz → 藍牙 AAC（含 48→44.1 kHz 重取樣） | 11–12% | 45–49% | 正常 |
| 同上＋全部 11 個音效（卸載機制加入前） | 12–13% | 87–100% | **過載**：2 秒的曲子要 2.6 秒才播完，聲音跟不上 |
| 同上＋全部 11 個音效（卸載機制加入後） | 13% | 55–56% | 約 2 秒內偵測到過載，重型音效自動暫停，斷音 0 |

**自動卸載**：核心 1 連續 2 秒達 90% 以上且有重型音效在跑時，重型音效暫停（輕量的留著），直到這次播放結束或換輸出；`st` 的 `fxshed` 為 1。這是通用的保護，任何過重的組合都適用，不限藍牙。LDAC 另有固定規則（一律暫停重型音效）。

## 2026-11-25 順播、場景循環、音量規則
- 工具：UART `dbg oc arm|show`（輸出端檢查：J=正弦預測跳變、Z=連續數位靜音，見 `docs/design.md`）、`dbg vol`、`dbg ramp`、`dbg looplen MS`、`dbg xfade MS`、`dbg spare 0|1`、`dbg opendelay MS`、`dbg scene 名稱|檔:音量`。
- 順播（48 kHz FLAC 三段切開的 997 Hz 正弦，6.5 秒）：開／關都是 312000 影格、0 跳變、0 靜音（環形緩衝多 0.5 秒緩衝，下一首開檔只要 5–10 ms）。22.05 kHz→48 kHz（重取樣）：關 = 每個接點 34 影格靜音＋2 個跳變；開 = 0。MP3（`-write_xing 1`）：總影格數正好 312000（延遲／填充已修剪），每個接點有一個約 30 LSB（峰值 808 的 4 %）的小階差，各段獨立編碼的緣故。`dbg opendelay 800`：開檔慢過緩衝（0.5 秒）就會有約 300 ms 空檔（開／關相同）。

- 場景記憶體（內部 RAM 剩餘／最大連續區塊，KB）：舊 → 新（in-place rewind）：場景 1 DAC 74.4/41.0 → 73.7/41.0，場景 2 DAC 75.6/43.0 → 74.9/41.0，廣播＋場景 1 45.9/31.7 → 45.0/31.7，廣播＋場景 2 46.5/31.7 → 46.0/31.7（最低點 41.6）。用 pc_loop 的備用解碼器（`dbg spare 1`）：場景 1 DAC 47.9/31.7，少 26 KB，廣播時會低於 35 KB，所以不用。

## 2026-11-25 FM 晶片後端（YM2151／YM2203，`components/fmvgm`）：合成流的量測
**全部數字都是合成暫存器流的數字**（`tools/hosttest/gen_fm_vgm.py` 產生，沒有任何真的 YM2151／YM2203 曲子可用）：「typical」每個聲部閘門時間 60 %、「dense」100 %（聲部首尾相接）、「靜音」= 晶片設定好了但從沒發音。研究（`docs/research/fm-chips-ymfm.md` §4.5）用 Mega Drive 真檔推算真曲子約為 dense 的 0.4–0.7 倍，沒有在這兩顆晶片上驗過。CPU 是 `st` 的 `cpu`（核心 0／核心 1，取穩定後的平均），「生產者成本」是 `dbg fm bench`／`dbg fm stat` 的「每秒音訊花的牆上時間」（含被別的任務搶走的時間）。板子：ESP32-S31 開發板，Wi-Fi 開著、Classic 藍牙 + BLE 都開著。

### A. 重取樣：播放器的 pc_rsq 要多少（研究 §10.2 A，用一般 WAV 檔）
單聲道 16 位元粉紅雜訊 WAV（4 s，`mode one` 重複），輸出 USB 小尾巴 48 kHz，沒有音效，`st` 的核心 1：
| 檔案 | 轉換 | 核心 1 | 比 48 k→48 k 多 |
|---|---|---|---|
| r48000.wav | 48000 → 48000（pc_rsq 不運轉） | 9 % | – |
| r55930.wav | 55930 → 48000（YM2151 的原生率） | 29–30 % | **+20 點** |
| r166400.wav | 166400 → 48000（YM2203 MIN 擬真度的輸出，比例 3.47） | 25–26 % | +16–17 點 |
研究估計 18–32 點，量到的在範圍內且偏下限。核心 0 都是 9–11 %、斷音 0。結論：這一項大到值得換。

### B. 生產者自己的成本（晶片 + 3:1 降取樣 + 重取樣，`dbg fm bench`，每串 20 秒，ms／秒音訊 = 一顆核心的 %）
輸出 48 kHz、24 階內插多相濾波器；晶片狀態在內部 RAM。核心 1 / 核心 0：
| 串流 | 未打補丁的 ymfm（核心 1／核心 0，原生率，無重取樣） | 打補丁後（原生率） | 打補丁後，輸出 48 kHz（最終韌體） |
|---|---|---|---|
| YM2203 typical | 523 / 535 | 535 / 546 | 528 / 538 |
| YM2203 dense | 532 / 544 | 550 / 562 | 543 / 556 |
| YM2151 typical | 900 / 921 | 662 / 678 | 732 / 746 |
| YM2151 dense | 937 / 958 | 713 / 733 | 789 / 805 |
| YM2151 靜音 | 462 / 472 | 164 / 165 | 237 / 236 |
- ymfm 補丁（`components/fmvgm/SOURCE.md`）：YM2151 dense −24 %、typical −26 %、靜音 −64 %；YM2203 沒有變（沒有 PM、沒有閒置運算元可跳）。補丁逐位元不變：PC 上 26 個測試檔（含每個晶片家族 4 個隨機暫存器壓力流，有 SSG-EG、LFO、CSM、通道 3 模式）所有校驗和與未打補丁的相同，負對照（把跳過條件放寬到 0x3c0）在每個檔都被抓到。
- 重取樣器：24 階 +7 點（YM2151 dense 718 → 789；每階約 2.5 ms／秒），16 階 768、32 階 808、48 階 848（YM2151 dense，48 kHz）。pc_rsq 在播放器裡是 +16–20 點，所以便宜約 2.5–3 倍。
- 與研究的估計比：YM2151 dense 未打補丁 937 ms/s（研究：90–98 %）；YM2203 53–55 %（研究：17–49 %，偏高，因為還有 3:1 降取樣與 24 階濾波器）。
- **晶片狀態放內部 RAM 或 PSRAM**（研究 §10.2 B4）：Auracast 載入後內部 RAM 剩 75 KB／最大區塊 43 KB，當時的版本（要求配置後留 40 KB）把晶片狀態放進 PSRAM：YM2151 dense 953（對 713–718）、YM2203 dense 727（對 550）、靜音 219（對 164），**慢約 33 %**。現在的規則是「配置後最大內部區塊仍有 24 KB 就用內部 RAM」，Auracast 開著晶片狀態也放得進去（上表與下面的矩陣是這個狀態）。
- **PC 與板子逐位元相同**：同一個檔、同一個取樣率、同一個階數，晶片原始輸出總和（左／右）、輸出雜湊、濾波器表雜湊在 PC（x86-64，`test_fmvgm bench`）與板子（`dbg fm bench`）上完全一樣——試了 YM2203 typical／dense、YM2151 typical／dense／靜音、S98 的 YM2203 與 YM2151、輸出率 native 與 48000、核心 0 與核心 1，超過 50 組全部相同（例：YM2151 dense 20 s、48 kHz：sumL = −33397323，out_hash 116f4de5，table_hash ac11e25b；YM2203 typical：sumL = 18529386755，out_hash 3e6a9bd9）。同一個 VGM 與同樣事件的 S98 在 PC 上輸出雜湊相同。

### I. Auracast 開著時 `play`／`stop` 的 CPU lockup（已修，2026-11-26）
**現象**：`out cast` 後約每 2 秒 `play`／`stop`，約 30–55 次後核心 0 CPU lockup 重啟（mp3／flac／ogg／m4a 都一樣，與 FM 後端無關）。
**原因（已證實）**：panic 的 PC `0x400388e0` 不是 ROM，是 flash 映射的程式碼：`addr2line` 解成 `wr_btdm_coex_iso_end_int_handle`（IDF v6.1 `components/bt/porting_btdm/controller/btdm_common/src/btdm_coex.c:176`），例外原因 1（instruction access fault），第二個例外是 `panic_handler`。這個包裝函式由藍牙控制器在 ISO 事件結束的中斷裡呼叫，IDF 沒有給它 `IRAM_ATTR`（它呼叫的 `coex_end_int_handle` 在 IRAM 裡，`wr_btdm_coex_iso_protect_frame_thres_get` 也有 `IRAM_ATTR`，只有 `iso_start/end_int_handle` 漏了）。NVS 寫入（音量、設定 `g_set.last`、停止時的續播書籤）期間 flash cache 關閉；ISO 中斷剛好在這段時間進來就去取 flash 的指令 → 例外 → lockup。`play`／`stop` 每次都寫 NVS，所以才被誤認為與 play／stop 有關。
**證據**：(1) 不播放，只在廣播中交替 `vol 30`／`vol 31`（每次一次 NVS 寫入，每秒 2 次）：61、62、62 輪（約 122 次寫入）後同一個 PC、同一個 lockup；(2) `play`／`stop` 基準線 28、46、47 輪；(3) 修正後（見下）NVS 連打 300 輪（600 次寫入）0 次，play／stop 3 × 280 輪 0 次。
**修正**：`app/main/linker.lf` 用 linker fragment 把 `wr_btdm_coex_iso_end_int_handle`（與 start 版）放進 IRAM（`noflash`），不改 IDF 原始碼（`_start_int_handle` 目前沒被連結進來，列在 fragment 只是預防）；成本約 8 位元組 IRAM。這是真正的根因修正，不是緩解。
**驗證**：play／stop 週期 2 秒（`t.mp3`、`t.flac`、`t.ogg`、`t.m4a` 輪流），3 次 × 280 輪（為最差基準 47 的 5.9 倍）全數存活，`underflows=0`、`send_err=0`。副作用：`cast` 的 `gap_max_us` 由 11–12 ms 變成 30–32 ms（flash 寫入期間 esp_timer 任務被延後；之前根本撐不到那一刻），`underflows` 仍 0。
**沒查**：flash 擦寫時 10 ms 計時器延遲約 30 ms 對接收端的影響（沒有在 JukeDial 收聽下量）；控制器其他可能不在 IRAM 的回呼（這次的測試沒有再出現）。
